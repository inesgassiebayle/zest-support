# Database — PostgreSQL + Prisma

## Source of truth
[`../design/db.md`](../design/db.md) is the schema spec — 13 entities (`users`, `recipes`, `recipe_steps`, `ingredients`, `recipe_ingredients`, `labels`, `recipe_labels`, `recipe_images`, `collections`, `collection_recipes`, `weekly_plans`, `planning_entries`, `follows`). If code and that doc disagree, fix the doc and the code together in the same PR — don't let them drift.

## Conventions
- `uuid` primary keys everywhere (`id`), generated by Prisma/Postgres — never auto-increment ints.
- Join tables for every many-to-many relationship (`recipe_ingredients`, `recipe_labels`, `collection_recipes`) — don't store arrays or comma-separated IDs in a single column.
- Catalog tables (`ingredients`, `labels`) are separate from free text specifically so search/filter stays reliable — don't reintroduce free-text ingredient/label fields on `recipes`.
- No `password` field on `users` — Auth0 owns authentication. `auth0_sub` is the link between an Auth0 identity and the local user row.
- No `created_at`/`updated_at` in the current schema by design (kept simple for MVP). If you need them, add them as an additive Prisma migration — don't treat their absence as a bug to silently "fix."

## Migrations
- Every schema change is a Prisma migration (`prisma migrate dev --name <description>`), committed alongside the code that needs it.
- Never edit a migration that's already been applied/merged — create a new one instead.
- Migration names should describe the change (`add_recipe_prep_time`, not `update1`).

## Queries
- Prefer Prisma's relation includes/filters over N+1 loops in application code.
- For the `follows` self-referential relation (`follower_id`/`followed_id`, both → `users`), be explicit about direction in query names/variables (`following` vs `followers`) — it's easy to flip these by accident.
